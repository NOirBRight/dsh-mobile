# Cloudflare hosting and persistent pairing

## Executive recommendation

Use **Cloudflare Pages** for the static mobile shell at a stable hostname such as `app.noirbright.top`. Use a **named Cloudflare Tunnel** at a separate stable hostname such as `relay.noirbright.top` to reach a dedicated WebSocket gateway that handles only opaque encrypted tunnel frames and signaling. **Never publish or reverse-proxy the raw DSH web service on port 3080.** Prefer direct WebRTC DataChannels when connectivity permits, with an explicit policy allowing fallback only to an encrypted frame relay. An owned Aliyun VPS running the same sealed-frame relay is the main alternative when ownership, regional reach, or provider independence matters more than Cloudflare-managed ingress.

Cloudflare Workers and Cloudflare Access are **not required** for this architecture: Pages serves static files, Tunnel supplies stable ingress, and DSH's own pairing handshake, device token, and end-to-end frame sealing provide application identity and confidentiality.

## What Cloudflare provides

- [Cloudflare Pages](https://developers.cloudflare.com/pages/get-started/) provides static site hosting, and [Pages custom domains](https://developers.cloudflare.com/pages/configuration/custom-domains/) allow the shell to use an owned `noirbright.top` hostname.
- A [named Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/get-started/create-local-tunnel/) can route an owned hostname through DNS; the route creates a CNAME to `<UUID>.cfargotunnel.com`. Because the tunnel identity and configured hostname are stable, `cloudflared` can restart without changing the public hostname.
- Cloudflare supports proxied [WebSockets](https://developers.cloudflare.com/network/websockets/), but a WebSocket is not immortal: Cloudflare may restart edge servers and terminate existing connections. Clients therefore need keepalive, disconnect detection, backoff, and reconnection.
- A [Quick Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/do-more-with-tunnels/trycloudflare/) proxies requests through Cloudflare to localhost but generates a random `trycloudflare.com` subdomain. It is for testing/development, is limited to 200 in-flight requests, and does not support SSE. Its rotating URL makes it unsuitable for no-repeat pairing or a stored resume profile.

## Existing persistent-pairing behavior

Persistent identity is already distinct from transport lifetime. The client API describes `deviceToken` as permanent until revoked, sends it instead of the one-time code on resume, and allows an expired stored offer when a token exists ([client.ts](../packages/e2e-tunnel/src/client.ts#L13-L17), [client.ts](../packages/e2e-tunnel/src/client.ts#L71-L77), [client.ts](../packages/e2e-tunnel/src/client.ts#L164-L184)). The host issues the plaintext token once and thereafter authenticates it for reconnects ([handshake.ts](../plugins/pairing/src/handshake.ts#L12-L16), [handshake.ts](../plugins/pairing/src/handshake.ts#L70-L88)). Thus a dead WebSocket should trigger a new authenticated session, not a new pairing ceremony.

The host persists only SHA-256 token hashes, compares them safely, supports revocation, and saves atomically by writing a temporary file, renaming it, then setting mode `0600` ([tokens.ts](../plugins/pairing/src/tokens.ts#L1-L6), [tokens.ts](../plugins/pairing/src/tokens.ts#L81-L93), [tokens.ts](../plugins/pairing/src/tokens.ts#L128-L139)).

The current mobile client stores both the offer and plaintext `deviceToken` in `localStorage` and reconnects indefinitely with bounded exponential backoff ([tunnel.ts](../apps/mobile-web/src/tunnel.ts#L15-L16), [tunnel.ts](../apps/mobile-web/src/tunnel.ts#L46-L70), [tunnel.ts](../apps/mobile-web/src/tunnel.ts#L98-L127)). A production native wrapper should move the token to platform secure storage. A browser deployment should use the safest practical browser-backed credential storage and strong XSS controls; `localStorage` is readable by injected same-origin script. The stored resume profile should retain stable routing and trust-anchor data but **omit the one-time pairing code**.

## Transport fit and relay policy

The protocol already has a deliberately small client `FrameTransport` seam and adapters for WebSocket and WebRTC DataChannel ([transport.ts](../packages/e2e-tunnel/src/transport.ts#L1-L22), [transport.ts](../packages/e2e-tunnel/src/transport.ts#L207-L229), [transport.ts](../packages/e2e-tunnel/src/transport.ts#L244-L289)). The host mirrors that seam with `HostFrameTransport` and a WebSocket relay adapter ([host-transport.ts](../plugins/pairing/src/host-transport.ts#L1-L24), [host-transport.ts](../plugins/pairing/src/host-transport.ts#L28-L65)). Direct mode already runs the sealed handshake and application traffic over the DataChannel while the relay carries signaling only ([client.ts](../packages/e2e-tunnel/src/client.ts#L113-L148)).

Recommended policy:

1. Attempt direct WebRTC first.
2. If direct setup fails, fall back only when the profile explicitly permits an **encrypted sealed-frame relay**.
3. Reconnect either carrier using the persistent device token; never interpret carrier continuity as identity continuity.
4. Keep the public gateway narrow: rooms/signaling and opaque frame forwarding only, with no generic HTTP proxy to DSH or localhost:3080.

With that design, Cloudflare can observe connection metadata (hostnames, IPs, timing, sizes, and WebSocket lifecycle) and the ciphertext it forwards, but not sealed DSH application plaintext. By contrast, exposing DSH through a conventional TLS-terminating raw reverse proxy makes HTTP/WebSocket plaintext available at that proxy after TLS termination and broadens the remotely reachable application surface. An owned Aliyun VPS relay has the same end-to-end confidentiality property if it only forwards sealed frames; it changes who controls and observes relay metadata, not the need for reconnect logic or application-layer encryption.

## Cost and OSS distribution

As of the current first-party pricing and limits documentation, this design can run on Cloudflare's **$0 Free plan**, but “free” does not make every hostname model suitable for zero-setup OSS distribution:

- **Named Cloudflare Tunnel:** Tunnel is [available on all plans](https://developers.cloudflare.com/tunnel/), and publishing it does not require a paid Access plan ([published applications](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/)). It does require a Cloudflare account and a domain on Cloudflare to publish an application; the default limits include [1,000 tunnels per account and 25 active replicas per tunnel](https://developers.cloudflare.com/cloudflare-one/account-limits/). The generated `<UUID>.cfargotunnel.com` name is a DNS target, not a public hostname users can browse directly: it only proxies DNS records in the same account ([Tunnel DNS](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/dns/)). Therefore a user without a domain cannot obtain a stable public **named-Tunnel** hostname. A [Quick Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/) needs neither an account nor a domain, but its random `trycloudflare.com` URL, 200 in-flight-request cap, lack of SLA, and testing-only status make it unsuitable for persistent pairing.
- **Pages static hosting:** A Cloudflare account can publish a purely static shell at the stable, Cloudflare-provided `<PROJECT_NAME>.pages.dev` hostname, so neither the project nor each user needs to own a domain ([Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/)). Static asset requests are [free and unlimited](https://developers.cloudflare.com/pages/functions/pricing/). Relevant Free limits include 500 builds/month, 100 projects/account, 20,000 files/site, 25 MiB/file, and 100 custom domains/project ([Pages limits](https://developers.cloudflare.com/pages/platform/limits/)); Functions instead consume the Workers Free quota.
- **WebSockets and traffic:** Proxied WebSockets are [supported on all plans](https://developers.cloudflare.com/network/websockets/) with no separate WebSocket add-on. Cloudflare counts one HTTP upgrade request per connection and measures server-to-client WebSocket bytes as bandwidth, while its billing documentation says ordinary CDN bandwidth is [included on all plans with no bandwidth charge](https://developers.cloudflare.com/billing/understand/how-charges-accrue/). This does not cover optional metered products or the host's own ISP/origin costs; Cloudflare's [service-specific terms](https://www.cloudflare.com/service-specific-terms-application-services/) also allow it to limit disproportionate video or large-file CDN use. The [Free plan has no uptime SLA](https://www.cloudflare.com/plans/).
- **Custom hostnames:** Pages custom domains are included up to the Free-plan limit above, but the registrant must still own/control the domain; an apex must be a zone in the Pages account, while a subdomain may use an external DNS provider ([Pages custom domains](https://developers.cloudflare.com/pages/configuration/custom-domains/)). If “custom hostnames” means Cloudflare for SaaS customer domains, its Free plan [includes 100 hostnames, then charges $0.10 per additional hostname](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/plans/); customers still control and validate those names.

**OSS implication:** distribute one shared static shell on `pages.dev` for free, but do not make “every user gets a stable named Tunnel” the default promise. Users without domains need either a project-operated relay/hostname under a project-owned zone (which centralizes credentials, quotas, abuse handling, and availability), a different stable-hostname provider, or a documented bring-your-own-domain path.

## Decision

Adopt Pages plus stable `noirbright.top` hostnames and a named Tunnel-backed, dedicated opaque gateway. Preserve direct WebRTC and define encrypted relay fallback explicitly. Keep the Aliyun sealed-frame relay as a viable owned alternative. Do not use Quick Tunnel for persistent pairing, do not expose port 3080, and do not treat any long-lived WebSocket as the persistent identity.
